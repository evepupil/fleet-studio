# 演示数据 —— 规格（DESIGN.md 第 5 章之一）

> 先读完 `DESIGN.md` 全文。演示数据路独占 `apps/web/src/api/demo/**`。
> 目的：不起服务也能把三页每种状态画出来，截图和交互检查每次结果一致。所有数字由固定输入算出；**当前时刻固定**。
> 第一版演示数据（`records.ts`、`timelines.ts`、`scenarios.ts`、`scenarios.test.ts`）是基础：它的苦工、时间线、回报尽量原样保留，只按第二版的记录形状补字段。

## 3. 历史（`history.ts`，新写）

用固定种子的伪随机（`mulberry32(20260923)`，自己实现，十几行）生成 `DEMO_NOW` 之前 30 个本地日（含今天到 12:10 为止）的**已结束**任务，保证每次运行结果相同：

- 每天的任务数：工作日 24～40、周末 8～16（均匀随机取整）；今天按 12:10 已过去的比例折算。
- 创建时刻：当天本地 09:00～23:59 均匀随机；今天不晚于 `DEMO_NOW` 前 15 分钟。
- 项目权重：wiki-forge 25、cloudmind 20、inferforge 15、onaho-wiki 10、ui-studio 10、fleet-studio 20。
- 角色权重：worker 45、scout 20、reviewer 15、fixer 10、tester 7、collector 3。
- 池权重：dsf 60、glmf 20、luna 12、qwen27 8；`requestedPool`：10% 的任务点名了所在池，其余为 null。
- 结局：已完成 82%、失败 12%（失败原因在 model_error、timeout、runtime_error、exit_code 里均匀取）、已取消 6%。
- 运行次数：85% 一次，15% 两次（第二次是续接，接在第一次结束后 1～10 分钟排队、立即开跑，结局同上规则再取）。
- 每次运行：排队到开跑 0～90 秒；`runMs` 在 120 000～1 500 000 之间（取两个均匀随机数的较小值再线性映射，偏向短）；用量：输入 40 000～600 000、缓存读 = 输入 × 0.6～0.9、输出 2 000～40 000、缓存写 0、合计 = 三者之和、费用 null。已取消的运行 `runMs` 取正常值的 30%、用量取 30%。
- 标题：按角色从一张 10 条的标题表里轮流取，再拼「 #序号」保证唯一（例如「补齐配置校验的边界用例 #137」）。任务书用第一版的默认模板。
- 编号：`h` + 5 位（由序号换成 31 进制字符表 `abcdefghjkmnpqrstuvwxyz23456789`），和在跑那批不重复。
- 苦工记录的 `channel`、`modelName`、`model` 按所在池填。

导出：`historyWorkers`、`historyRuns`（`WorkerRecord[]`、`RunRecord[]`）。

## 4. 场景（`scenarios.ts`）

`DemoScenarioName = "busy" | "empty" | "failure" | "offline" | "disabled"`。`buildDemoScenario(name)` 返回：

```ts
interface DemoScenario {
  config: FleetConfig;
  projects: ProjectRecord[];
  workers: WorkerRecord[];
  runs: RunRecord[];
  snapshot: Snapshot;                          // 用 core 的 buildSnapshot + queuePositions 算
  details: ReadonlyMap<string, WorkerDetail>;  // 每个苦工都有（历史的也要，任务页点开能看）
  timelines: ReadonlyMap<string, TimelineEvent[]>; // 只有第一版那 5 个运行有事件，其余为空数组
  connection: "open" | "lost";
}
```

| 场景 | 内容 |
|---|---|
| busy | 第 2 节在跑的一批 + 第 3 节历史；连接正常 |
| empty | 没有任何苦工和项目；配置同上 |
| failure | 第一版 failure 的 26 个苦工（池 glm 改 glmf，按第 2 节规则补字段）+ 历史；`configError` 用第一版那句 |
| offline | 同 busy；演示源先报 `open`，300 毫秒后报 `lost` |
| disabled | 同 busy，但四个池全部 `enabled: false`；另把公共排队从 3 个加到 5 个（再加 2 个：项目 cloudmind、onaho-wiki，角色 tester、worker，标题「给统计口径补夏令时用例」「整理 wiki 首页的导航」） |

调度输入（`limits`、`running`、`queued`）在 `api/demo/scheduling.ts` 里按服务端同样的规则组装：`limits` 取配置顺序带 `enabled` 和 `poolRuntimes`；`queued` 的 `requestedPoolId = worker.poolId`。

## 5. 数据源（`demoSource.ts`）

`createDemoDataSource(name: DemoScenarioName): DataSource`，在内存里持有一份可变的配置和记录：

- `subscribeSnapshot`：立即回调当前快照和连接状态（offline 的时序见上）；之后每次改设置都重算快照并回调所有订阅者。
- `subscribeWorker`：在 `details` 里找得到就依次回调详情和全部事件；找不到回调 `onNotFound`。
- `fixedNow()`：`DEMO_NOW_MS`。
- `getStats(query)`：延迟 150 毫秒后返回 `computeStats`（core）的结果：事实从当前记录转换（`api/demo/facts.ts`：`RunRecord` → `RunFact`、`WorkerRecord` → `WorkerFact`），`labels` 用第 1 节的名字和配色。
- `getTasks(query)`：延迟 150 毫秒后返回 `queryDemoTasks(summaries, query, DEMO_NOW_MS, tz)`（`api/demo/taskQuery.ts`，纯函数）的结果。摘要用 core 的 `buildWorkerSummary` 从当前记录算。筛选、排序语义和服务端一致（见 `docs/模块设计/服务层-存储.md` 第二版 D 节的 `TaskRepo.query`）：状态按最新运行、`active`、`retrying`、项目 / 池 / 角色 / 渠道 / 模型、时间按创建时间（`resolveRange`）、标题包含（不区分大小写）；排序值相同按编号；`limit` 条一页；游标就是下一页起始下标的字符串，解不开抛 `Error("翻页参数无效，请从第一页重新加载")`。
- `getProjects()`：项目按名字排序。
- `setPoolEnabled(id, enabled)`：延迟 300 毫秒；池不存在抛 `Error("池不存在：<id>")`；否则改配置、重算快照、通知订阅者，返回该池视图。
- `reorderPools(ids)`：延迟 300 毫秒；不是当前全部池的一个排列就抛 `Error("池的列表已经变了，请刷新后再调顺序")`；否则重排、重算、通知，返回全部池视图。

## 6. 单测（`scenarios.test.ts`、`taskQuery.test.ts`、`history.test.ts`）

断言写具体数字，并在回报里把下面这些数列成一张表（主控拿去填各页的交互检查）：

- busy：`live` 五个数、`sharedQueued`、四个池各自的 `running`、`queued`、在跑格子里重试的个数、快照 `workers` 里进行中的个数。
- busy 的统计（固定 +480）：`range=all` 的 `total.tasks`、`total.usage.totalTokens`、`today.tasks`；四个维度下 `tokenShare` 的项数；`range=today` 的 `granularity` 和 `buckets.length`；`range=7d` 的 `buckets.length`。
- busy 的任务查询：默认（进行中）的 `total`；`status=all` 的 `total` 和第一页条数（50）；按标题搜 busy 在跑那批里某个唯一标题的一段（写出你用的那段文字）后的 `total`（应为 1）。
- disabled：四个池 `enabled` 都是 false、`live.slotsTotal` 为 0、`sharedQueued` 为 5。
- empty：`live` 全 0，统计 `total.tasks` 为 0、`buckets` 为空。
- history：同一种子两次生成完全相同；没有编号冲突；每个运行 `endedAt ≥ startedAt ≥ queuedAt`；续接运行的排队时间晚于上一次的结束时间。
- 数据源：`reorderPools` 后快照池顺序改变；传错排列时抛错；`setPoolEnabled` 后订阅者收到新快照。
