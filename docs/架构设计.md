# fleet-studio 架构设计

## 1. 总体与分层

```text
 主会话 ─读─▶ 接入层：fleet 系列 skill（怎么谈设计、什么活外包、怎么派、怎么验、怎么记）
                │ 教主会话怎么用下面的 fleet 命令
 用户 ─浏览器─▶ 界面层：控制台看板 ── SSE / HTTP（改设置带看板令牌）┐
 主会话 ─fleet─▶ 命令行层：fleet 命令 ─── HTTP（带本机令牌）──────┤
                                                                   ▼
 ┌──────────────────────────── 服务层：闸门服务 ────────────────────────────┐
 │ 接口：路由、校验来源、SSE 推送、托管看板静态文件                         │
 │ 调度引擎：派活 → 排队 → 放行 → 跟踪 → 收尾；超时、取消、续接、重启接管   │
 │ 存储：SQLite（项目 / 苦工 / 运行）      进程托管：拉起、读输出、杀进程树 │
 └──────────────────────────────────────────────────────────────────────────┘
          │ 所有规则判断都调用 ▼                    │ 分离启动，输出写文件
 ┌──────── 核心层（纯函数，零 IO）────────┐         ▼
 │ 领域模型与配置   容量调度与生命周期     │   外部：pi / opencode 苦工进程
 │ 运行时适配（参数 + 事件流解析）  快照汇总 │         │
 └─────────────────────────────────────────┘         ▼
                                              外部：mcgrox 等模型通道
```

| 层 | 代码 | 模块 | 职责 | 可以依赖 |
|---|---|---|---|---|
| 接入层 | `skills/`、`roles/` | [skill 与苦工提示词](模块设计/接入层-skill与苦工提示词.md) | 注入模型上下文的规矩：给主会话的 skill（谈设计、派活、开发 / 界面 / 评审流程、运维），给苦工的角色提示词 | 只写命令行层的用法，门禁核对两边一致；角色提示词由配置引用 |
| 核心层 | `packages/core` | [领域模型与配置](模块设计/核心层-领域模型与配置.md)、[容量调度与生命周期](模块设计/核心层-容量调度与生命周期.md)、[运行时适配](模块设计/核心层-运行时适配.md)、[快照汇总](模块设计/核心层-快照汇总.md)；第二版新增「统计口径」（开发时建） | 所有「规则」：该不该放行、先派给哪个池、状态怎么走、事件流是什么意思、看板该显示什么、统计怎么分段和合并 | 无 |
| 服务层 | `packages/daemon` | [存储](模块设计/服务层-存储.md)、[进程托管](模块设计/服务层-进程托管.md)、[调度引擎](模块设计/服务层-调度引擎.md)、[接口](模块设计/服务层-接口.md) | 所有「动作」：落库、拉进程、读文件、推送、响应请求 | 核心层 |
| 命令行层 | `packages/cli` | [fleet 命令](模块设计/命令行层-fleet命令.md) | 把主会话的命令翻译成接口请求，把结果排成好读的文字 | 核心层（仅类型和纯函数） |
| 界面层 | `apps/web` | [工作区看板](模块设计/界面层-工作区看板.md)（第一版）；第二版按页面建：控制台框架、总览、槽位、任务（开发时建） | 把快照、统计、任务列表和时间线画出来；槽位页发出启停和调顺序 | 核心层（仅类型和纯函数） |
| 测试支撑 | `packages/testkit` | [假苦工](模块设计/测试支撑-假苦工.md) | 按剧本模拟 pi / opencode 的输出，给集成测试和演示用 | 无 |

分层的用意：规则和动作分开。规则全在核心层，是纯函数，可以穷举测试；服务层只负责「按规则去做」，出了问题容易分清是规则错了还是动作错了。

## 2. 两条主路径

### 2.1 派活路径

```text
fleet run ─▶ POST /api/workers ─▶ 调度引擎.submit
   校验池、角色、目录 ─▶ 存储：建项目（首次）、建苦工、建第 1 次运行（排队中），任务写入 runs/<编号>.task.md
   ─▶ 触发一次放行
放行：核心.planDispatch(各池上限, 在跑, 排队) ─▶ 得到要放行的运行
   ─▶ 核心.运行时适配.buildLaunch 生成参数 ─▶ 进程托管.spawn（分离启动，输出写文件）
   ─▶ 存储：运行改为工作中，记下进程号
跟踪：每 400 毫秒读一次输出文件的新增部分 ─▶ 核心.事件流解析器.push
   ─▶ 新的时间线事件推给正在看这个苦工的页面；用量、最近活动、重试信息节流写库
收尾：进程退出 ─▶ 读完剩余输出 ─▶ 核心.resolveRunOutcome ─▶ 存储：写结局、回报原文
   ─▶ 槽位释放 ─▶ 再触发一次放行 ─▶ 正在 fleet wait 的请求返回结果
```

### 2.2 观察路径

```text
浏览器打开 http://127.0.0.1:4870
   ─▶ 静态页面 ─▶ GET /api/stream（SSE）先收到完整快照，之后每次变化收到新快照（最快 300 毫秒一次）
   ─▶ 点开一个苦工 ─▶ GET /api/workers/:id 取详情
   ─▶ GET /api/workers/:id/stream?after=<位置>（SSE）接收时间线增量
```

第二版在这条路径上多了两类普通请求：

```text
总览页 ─▶ GET /api/stats?from=&to=&dimension=
   ─▶ 存储：按时间段和维度在库里求和（按索引）─▶ 核心层：分段、补空段、前 8 名合并「其他」─▶ 返回
   ─▶ 快照里出现「有任务开始或结束」时重新请求（最快 5 秒一次）
任务页 ─▶ GET /api/tasks?筛选&排序&cursor= ─▶ 存储：按索引查一页 50 条 ─▶ 返回这一页和下一页的游标
   ─▶ 快照变化时重新拉第一页（最快 2 秒一次）；进行中的行直接用快照里的数据刷新
```

快照由核心层的 `buildSnapshot` 从存储里的记录算出来：容量条每一格属于谁、每个项目各状态几个、今日用量、最近 10 分钟健康情况，都在这一步算好，页面只管画。

### 2.3 改设置路径（第二版）

```text
槽位页点「停用」或「上移」─▶ PATCH /api/pools/:id 或 PUT /api/pools/order（带看板令牌）
   ─▶ 接口：核对看板令牌只用于这两个接口
   ─▶ 配置存储：备份当前配置 ─▶ 改池的启用或顺序 ─▶ 写临时文件再改名替换
   ─▶ 配置热更新 ─▶ 调度引擎重新放行（停用的池不再接新活，在跑的不打断）
   ─▶ 新快照推给所有看板页面（命令行或手改配置文件也走同一条热更新，页面同样跟着变）
```

## 3. 状态流转

```text
            ┌──────────── 取消 ────────────┐
            │                              ▼
 排队中 ─放行─▶ 工作中 ─正常收尾─▶ 已完成
   │              ├─通道错误重试耗尽 / 运行时报错 / 异常退出 / 超时 / 接管不了─▶ 失败
   │              └─取消─▶ 已取消
   ├─取消─▶ 已取消
   └─排队超时─▶ 失败
```

- 三个终态（已完成、失败、已取消）不能再变。续接会新建一次运行，旧运行保持原样。
- 「重试中」是工作中的附加标记，不单独算状态。
- 苦工的状态 = 它最新一次运行的状态。

## 4. 容量调度规则

第二版起，池按优先级（配置里的先后）逐个计算：

1. 停用的池跳过。空位 = 容量 − 该池在跑数，空位 ≤ 0 也跳过（容量调小后的超额不打断在跑的苦工）。
2. 这个池的候选 = 点名它的排队 + 没点名的排队（公共排队）。
3. 有空位时，从候选里「有排队、且没到单项目上限」的项目中挑在这个池在跑数最少的；并列时挑队首排得最早的；放行它队首的那个运行，没点名的就此分配到这个池；重复直到没有空位或没有候选。
4. 同一项目内部严格先来先到。
5. 续接视同点名原来的池。点名的池停用时，派活和续接当场报错；停用前已经在排的点名任务继续等，池重新启用后照常放行。

## 5. 服务重启与接管

服务启动时：

1. 排队中的运行保持排队，正常参与放行。
2. 工作中的运行逐个检查进程：进程号存在且映像名与启动时记录一致，就重新接管——从头解析它的输出文件还原状态，之后按轮询判断何时结束（接管的进程拿不到退出码，结局只按事件流判定）。
3. 进程已经不在：先把输出文件读完；事件流里已经给出正常收尾的，算已完成；否则算失败，原因「服务重启后接管不了」。

## 6. 出错隔离

- 单个苦工的输出解析出错，只记一条错误事件，不影响其他苦工，也不让服务退出。
- 进程托管的任何异常都转成该运行的失败，写明原因。
- 配置文件改坏了：服务继续用上一份有效配置，在日志和看板顶部提示错误所在（`fleet pools` 不显示）。

## 7. 扩展点

| 要加的东西 | 改哪里 |
|---|---|
| 新的苦工运行时 | 核心层加一个运行时适配器；服务层加一条可执行文件探测规则 |
| 新角色 | 只改配置文件 |
| 新模型池 | 只改配置文件 |
| 通道出错失败后自动换池重跑 | 调度引擎在失败收尾时按优先级找下一个启用的池，新建一次运行；核心层补规则和单测 |
| 命令行停用池、调顺序 | 命令行层加两个子命令，调用 2.3 的两个接口（用本机令牌） |
| 通道熔断 | 核心层 `planDispatch` 的输入加上池的暂停状态；调度引擎根据最近失败计算暂停 |
