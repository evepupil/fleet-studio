# 服务层 · 调度引擎与装配

> 模块定位：派活 → 排队 → 放行 → 跟踪 → 收尾的全流程，以及把配置、存储、进程托管、引擎、接口装配成一个常驻服务 · 对应代码：`packages/daemon/src/engine/`、`packages/daemon/src/app/`、`packages/daemon/src/config/`、`packages/daemon/src/main.ts` · 所属里程碑：[M1 闸门服务与 fleet 命令](../roadmap.md#m1)（过期清理在 [M3](../roadmap.md#m3) 验收）· 状态：待集成测试 · 最近更新：2026-09-23

## 1. 职责与边界

- **管：** 实现 `FleetService`（`engine/service.ts`）；放行循环；每次运行的跟踪与收尾；超时；取消；续接；等待；时间线；快照；重启接管；过期清理；配置热更新；服务启动与退出。
- **不管：** 规则本身（全部调用 `@fleet/core`）；SQL（存储层）；操作系统细节（进程托管层）；HTTP（接口层）。
- 依赖的契约：`store/types.ts`、`process/types.ts`、`app/types.ts`、`engine/service.ts`。

## 3. 引擎规格

### 3.1 `createEngine(deps)`

```ts
interface EngineDeps {
  repos: Repos;
  host: ProcessHost;
  config: ConfigStore;
  paths: DaemonPaths;
  logger: Logger;
  version: string;
  startedAt: string;
  getPort: () => number;
  platform: "win32" | "posix";
  /** 展开 ~ 用 */
  homeDir: string;
  /** 展开 builtin: 用，即 fleet-studio 仓库根目录 */
  builtinRoot: string;
  /** 默认 Date.now，测试可注入 */
  now?: () => number;
  /** HTTP 收到退出请求后调用 */
  onShutdownRequested: () => void;
}
interface Engine extends FleetService {
  /** 接管 → 过期清理 → 启动定时器 → 放行一次 */
  start(): Promise<void>;
  /** 停掉定时器、放弃跟踪；苦工进程继续运行，等下次启动接管 */
  stop(): Promise<void>;
}
```

### 3.2 派活 `submit(request)`

1. 取配置：池 = `request.pool ?? defaults.pool`，角色 = `request.role ?? defaults.role`，运行时 = `request.runtime ?? defaults.runtime`。池、角色不存在 → `invalid_request`；`getRuntimeAdapter(运行时).displayModel(池)` 为 null → `invalid_request`「池 <id> 没有为 <运行时> 指定模型」。
2. 路径：`normalizeProjectPath(projectPath, platform)` 和 `normalizeProjectPath(cwd, platform)`；工作目录必须存在且是目录，否则 `invalid_request`「工作目录不存在：<cwd>」。
3. 项目：按 `projectKeyOf` 取；没有就新建，`colorIndex = pickColorIndex(projects.colorIndicesInUse(7 天前), key)`，`name = projectNameOf(path)`。
4. 苦工：编号用 `createWorkerId()`，撞了重试；标题 = `request.title ?? 正文第一个非空行压成一行截到 40 字`；`model = displayModel`；`thinking = request.thinking ?? defaults.thinking`；pi 的 `sessionRef = piSessionIdOf(编号)`，opencode 为 null；`latestRunSeq = 1`。
5. 第 1 次运行：排队中，`timeoutMs = resolveRunTimeoutMs(config, 池, request.timeoutMin)`，`queueTimeoutMs = resolveQueueTimeoutMs(config, 池, request.queueTimeoutMin)`，用量为零，`eventCount = 0`。
6. 项目、苦工、运行在一个事务里写入。之后刷新时间线（出现 `run_start`）、发事件、请求放行，返回摘要。

### 3.3 续接 `send(id, request)`

苦工不存在 → `not_found`；最新运行不是终态 → `conflict`「苦工还在排队或工作中，等它结束后再追加指令」；opencode 且 `sessionRef` 为 null → `conflict`「会话还没建立，无法续接」。新建第 `latestRunSeq + 1` 次运行（超时按苦工所在池和 `request.timeoutMin` 算，排队超时取池和全局默认），更新 `latestRunSeq`，同样写事务、刷新时间线、发事件、请求放行。

### 3.4 放行循环

- `requestDispatch()`：用 `setImmediate` 合并短时间内的多次请求；同一时刻只跑一轮。另有每秒一次的兜底。
- 一轮：
  1. 读活跃运行和它们的苦工。
  2. 排队中、但苦工所在的池已不在配置里的运行 → 失败 `pool_removed`，说明「所在的池 <id> 已从配置中删除」。
  3. 上限取配置里各池；在跑列表 = 状态为工作中的运行（含正在启动的）；调用 `planDispatch`。
  4. 对每个要放行的运行：**先**把状态改成工作中、写 `startedAt`（占住槽位，防止下一轮重复放行），再交给启动器。

### 3.5 启动 `launcher`

1. 角色：配置里找不到（被删了）就用只有编号的空角色，记一条警告。`expandRolePaths(角色, { home: homeDir, builtinRoot })`。
2. opencode 且 `opencodePromptPath(角色)` 非 null：读这个文件作为 `rolePromptText`；读不到 → 该运行失败 `spawn_error`「读不到角色提示词：<路径>」。
3. `adapter.buildLaunch({ prompt: 运行.prompt, runDir: paths.runDir(运行编号), cwd, title, sessionRef, isContinuation: seq > 1, thinking, pool, role, rolePromptText })`。
4. `host.resolve(运行时)`，`host.workerEnv()`，`host.spawn({ command, args, cwd, env, stdoutPath: outFile, stderrPath: errFile, files })`。
5. 成功：写 `pid`、`processImage`，建跟踪器，注册 `onExit`。
6. 任何一步抛错：该运行失败 `spawn_error`，说明取错误信息；请求放行（槽位已空出）。
7. 启动期间被取消（见 3.9）：拿到进程号后立刻结束它。

### 3.6 跟踪 `runTracker`

引擎用一个 400 毫秒的定时器轮询所有跟踪器（不要每个跟踪器一个定时器）。每个跟踪器每次：

1. 依次读 stdout、stderr 文件的新行，逐行交给解析器（`stream` 分别为 `stdout`、`stderr`，`at` 为当前时间）。
2. 新产出的草稿追加到 `timeline.jsonl`（每行一个草稿 JSON），并交给时间线缓存（3.10）。
3. 进展有变化时落库（`usage`、`retry`、`activity`、`lastActivityAt = progress.lastEventAt`、`finalText`、`eventCount`），同一运行最多每秒一次；阶段、重试信息、结局发生变化时立即落库。落库后发 `worker` 和 `snapshot` 事件。
4. opencode：`progress.sessionRef` 非 null 而苦工的 `sessionRef` 还是 null → 立即写入苦工（这样即使本次运行失败，也能续接）。
5. `progress.phase === "ended"` 后 10 秒进程仍未退出 → `host.kill(pid)`（`killedBy` 保持 null，结局以事件流为准）。
6. 进程退出（`onExit` 触发，或接管的进程在 2 秒一次的存活探测里发现已不在）→ 把两份文件读完、`flush` 出最后半行也交给解析器 → 收尾（3.7）。
7. 每个跟踪器的处理包在 `try/catch` 里：出错只记日志，不影响其他跟踪器。

### 3.7 收尾 `finisher`

```text
resolveRunOutcome({ progress, exit, killedBy: 库里运行的 killedBy, timeoutMs })
```

`exit`：有退出信息时 `{ kind: "exited", code, signal }`，接管后发现进程已不在时 `{ kind: "lost" }`。然后 `assertTransition(当前状态, 结局状态)`，一次性写入：状态、失败原因、说明、`endedAt`、`exitCode`、最终用量、`retry = null`、`activity`、`finalText`、`eventCount`。刷新时间线（出现 `run_end`）、发事件、唤醒等待者、请求放行。

### 3.8 超时 `timeouts`

每秒一次，对活跃运行调用 `findExpired(运行, now())`：

- `timeout`：进程号已知 → 写 `killedBy = "timeout"` 再 `host.kill(pid)`，由退出流程收尾；进程号还没拿到 → 这一轮跳过。
- `queue_timeout`：直接收尾为失败 `queue_timeout`，说明「排队超过 N 分钟」。

### 3.9 取消 `cancel(id)`

- 最新运行排队中 → 直接收尾为已取消，说明「已被取消」。
- 工作中 → 写 `killedBy = "cancel"`；进程号已知就 `host.kill(pid)`，还在启动就做标记（3.5 第 7 步）。之后最多等 5 秒让退出流程收尾，再返回最新摘要。
- 已是终态 → 原样返回。

### 3.10 时间线 `timelineStore`

- 一个苦工的完整时间线 = `assembleTimeline(每次运行 + 它的草稿)`，保证和从磁盘重新加载的结果一致。
- 草稿来源：在跑的运行用内存里的；已结束的读 `runs/<运行编号>/timeline.jsonl`；这个文件不存在（例如接管前就结束了）时，用新的解析器把 `out.jsonl`、`err.log` 从头解析一遍（时间用运行的 `startedAt`）。
- 缓存最近用过的 50 个苦工的完整时间线；在跑的苦工常驻缓存。
- 刷新（新草稿、运行开始、运行结束、新建运行时调用）：重新拼接，比原来多出来的尾部事件用 `timeline` 事件发出。时间线只会在尾部增长。
- `timeline(id, after, limit)`：返回 `seq > after` 的前 `limit` 条，`next` 为最后一条的 `seq`（没有就是 `after`），`total` 为总条数。

### 3.11 快照 `snapshotService`

- 查询口径照 [快照汇总](核心层-快照汇总.md) 3.1：活跃运行 + 结束时间晚于 `min(今日零点, now − snapshotWindowHours, now − 10 分钟)` 的运行 + 今日开跑的运行，涉及的苦工及其全部运行，全部项目。
- 排队位置：用 `queuePositions`（上限取配置，在跑和排队条目带上苦工的池和项目）。
- 今日零点按本机时区。
- 有任何变化时标记「脏」；`snapshot()` 在不脏且距上次计算不到 5 秒时返回缓存（健康窗口会随时间变化，所以最多 5 秒重算一次）。

### 3.12 等待 `waiter`

先检查编号是否都存在（不存在 `not_found`）；条件已满足立即返回；否则登记等待者，每次相关苦工的 `worker` 事件后重查；满足、超时或中止信号触发时返回 `WaitResult`：`done` 为已是终态的摘要（按请求顺序），`pending` 为其余编号，`timedOut` 为条件是否未满足。

### 3.13 其余接口方法

- `listWorkers`：`project` 参数先归一化成项目键；按创建时间倒序取 `limit` 个，算摘要，再按 `status` 过滤。
- `getWorker`：`buildWorkerDetail`。
- `pools()`：取快照里的池视图。`patchPool`：`config.save(applyPoolPatch(...))`，返回新快照里的该池视图。
- `roles()`：配置里的角色。`health()`：版本、启动时间、进程号、数据目录、端口。
- `requestShutdown()`：调用 `deps.onShutdownRequested`。
- 配置变化：`host.invalidate()`、快照标脏、发 `snapshot` 事件、请求放行。

### 3.14 服务启动时接管 `recovery`

对每个工作中的运行：

- 没有进程号（上次服务在启动它的途中退出）→ 失败 `interrupted`，说明「服务在启动苦工时退出」。
- `host.isAlive(pid, processImage)` 为真 → 接管：新建解析器，从头重新解析两份输出、重写 `timeline.jsonl`，之后按 2 秒一次探测存活。
- 否则：从头解析两份输出后直接收尾，`exit = { kind: "lost" }`（输出里已经正常收尾的会被判为已完成）。

排队中的运行不用处理，正常参与放行。

### 3.15 过期清理 `retention`

启动时和之后每小时：`cutoff = now − retentionDays 天`；`listExpiredWorkerIds(cutoff)` 得到的苦工，删掉它们全部运行的 `runs/<运行编号>/` 目录，再删库里的记录；最后 `deleteOrphansCreatedBefore(cutoff)`。记一条日志写明删了多少。

### 3.16 出错隔离

所有定时任务、事件回调、跟踪器处理都包 `try/catch` 并记日志；任何单个苦工的问题不能让服务退出。

## 4. 装配规格

### 4.1 `resolveDaemonPaths(home)`

`config.json`、`daemon.json`、`fleet.db`、`daemon.log`、`runs/` 都在 `home` 下；单次运行的文件见 `app/types.ts` 注释。

### 4.2 `openConfigStore(file, logger)`

- 文件不存在：写入 `DEFAULT_CONFIG`（两空格缩进 JSON）再读。
- 首次读取不合法 → 抛 `FleetError("config_invalid", "配置文件有错：<问题列表>")`，服务不启动。
- 之后每秒检查一次文件修改时间：变了就重新解析；合法 → 替换当前配置、清空错误、通知；不合法 → 保留上一份有效配置、记下错误说明（问题列表用「；」连接）、通知。
- `save(config)`：写文件（两空格缩进），立即替换当前配置，并记下这次写入后的修改时间，避免被自己的轮询当成外部修改再通知一遍。

### 4.3 `startDaemon(options)`

```ts
interface StartDaemonOptions {
  home: string;
  /** 不传用配置里的端口；测试传 0 */
  port?: number;
  repoRoot: string;
  /** 看板构建产物目录，默认 <repoRoot>/apps/web/dist */
  webDistDir?: string;
  version: string;
}
interface DaemonHandle { port: number; token: string; home: string; stop(): Promise<void> }
```

1. 建好 `home` 和 `runs/`；创建日志。
2. 单实例：`daemon.json` 存在、进程号还活着、且 `/api/health` 能通 → 抛 `FleetError("conflict", "服务已在运行（端口 <端口>）")`。
3. 打开配置、数据库（`createRepos`）、进程托管（`createProcessHost`）。
4. 令牌：24 字节随机数的十六进制。
5. 创建引擎、HTTP 应用，按端口启动 HTTP（端口被占用 → 抛 `FleetError("conflict", "端口 <端口> 被占用")`）。
6. 写 `daemon.json`（进程号、实际端口、令牌、启动时间、版本、数据目录）。
7. `engine.start()`。
8. `stop()`：引擎停止 → HTTP 关闭 → 数据库关闭 → 配置关闭 → `daemon.json` 里的进程号还是自己时删掉它。可重复调用。

### 4.4 `main.ts`

- 参数：`--home <目录>`、`--port <端口>`。`home` 缺省为环境变量 `FLEET_HOME`，再缺省为 `<用户目录>/.fleet-studio`。
- `repoRoot` = 本文件所在目录往上三级（`packages/daemon/dist/main.js` → 仓库根）；版本取 `packages/daemon/package.json`。
- 收到 `SIGINT` / `SIGTERM` 或退出请求：`stop()` 后以 0 退出。未捕获异常：记日志后以 1 退出。

## 5. 验证方式

- **引擎单测**（`packages/daemon/test/engine/`，引擎路负责）：内存数据库（`createRepos(":memory:")`）+ 假进程托管（实现 `ProcessHost`，可手动推送输出行和退出）+ 假配置存储。覆盖派活校验与建档、放行占位、启动失败、跟踪落库节流、收尾各分支、取消三种情况、续接、超时两种、`ended` 后强杀、等待三种返回、时间线增量与重新加载一致、快照缓存、接管三种情况、过期清理、池被删除。
- **装配单测**（`packages/daemon/test/app/`，装配路负责）：路径布局；日志轮转；配置首次生成、非法、热更新（合法 / 不合法）、保存不触发重复通知；`daemon.json` 读写与只删自己的。
- **集成测试**（`packages/daemon/test/integration/`，测试路负责，在前两路完成后）：临时数据目录 + 端口 0 起真服务，运行时命令指向假苦工，逐条验证：
  1. 容量 3 的池同时派 9 个，任何时刻在跑不超过 3（按轨迹算）。
  2. 甲项目占满 3 个并排队 3 个后，乙项目派 2 个：下一个空位先给乙。
  3. 成功剧本：已完成、回报结论通过、用量累加、时间线含工具调用和结果。
  4. 模型错误、缺密钥、崩溃三种失败的原因与说明。
  5. 重试风暴：判为 `model_error` 且进程被结束。
  6. 运行超时：失败 `timeout`，进程（含子进程）被结束。
  7. 取消排队中和工作中的苦工。
  8. 续接：第 2 次运行复用会话（pi 的 `--session-id` 不变；opencode 带上首次运行的会话编号）。
  9. 重启接管：服务停掉时苦工继续跑，新服务起来后接着跟踪直到完成；服务停掉期间结束的苦工按输出判定结局。
  10. 调整容量后立即多放行。
  11. 快照里排队中的苦工带排队位置；全局 SSE 首条是快照。
