# 核心层 · 容量调度与生命周期

> 模块定位：决定「这一刻放行谁」「谁超时了」「状态能不能这么变」「这次运行最终算什么结局」 · 对应代码：`packages/core/src/{scheduling,lifecycle}/` · 所属里程碑：[M0 工程骨架与领域核心](../roadmap.md#m0) · 状态：已完成 · 最近更新：2026-09-24

## 1. 职责与边界

- **管：** 公平放行的排序与计划、排队位置、超时判定、状态流转合法性、运行结局判定。全部是纯函数：输入列表和时间，输出决定。
- **不管：** 真正去拉进程、杀进程、写库（调度引擎的事）；解析事件流（运行时适配的事）。

## 2. 结构与数据流

```text
调度引擎每次触发放行：
  各池上限 + 在跑列表 + 排队列表 ─▶ planDispatch ─▶ 要放行的运行编号（按放行顺序）
快照汇总需要排队位置：
  同样的输入 ─▶ queuePositions ─▶ 运行编号 → 第几个被放行
调度引擎每秒检查一次：
  排队中 / 工作中的运行 + 当前时间 ─▶ findExpired ─▶ 超时名单
进程结束时：
  事件流进展 + 进程退出信息 + 谁结束的它 ─▶ resolveRunOutcome ─▶ 终态、失败原因、说明
```

## 3. 规格

### 3.1 类型

```ts
interface PoolLimit { poolId: string; capacity: number; perProjectCap: number | null }
interface RunningEntry { runId: string; poolId: string; projectKey: string }
interface QueuedEntry { runId: string; poolId: string; projectKey: string; queuedAt: string }
interface DispatchOrder {
  /** 按公平规则依次可以放行的运行编号（不考虑还剩几个空位） */
  eligible: string[];
  /** 因单项目上限被挡住的运行编号，按排队时间先后 */
  blocked: string[];
}
```

### 3.2 `dispatchOrder(limit, running, queued): DispatchOrder`

只看 `poolId === limit.poolId` 的条目。

1. 每个项目的排队按 `queuedAt` 升序，相同再按 `runId` 字典序，形成先来先到的队列。
2. `count[项目]` 初值 = 该项目在这个池里的在跑数。
3. 循环：候选 = 队列非空且（`perProjectCap` 为 null 或 `count < perProjectCap`）的项目。没有候选就停。
   - 选 `count` 最小的项目；并列选队首 `queuedAt` 最早的；再并列选 `projectKey` 字典序小的。
   - 把它的队首放进 `eligible`，`count` 加一，出队。
4. 剩下的全部进 `blocked`，按 `queuedAt`、`runId` 排序。

注意：排序本身不看容量还剩几个空位。

### 3.3 `planDispatch(limits, running, queued): string[]`

按 `limits` 的顺序逐池处理：空位 = `capacity` − 该池在跑数；空位 ≤ 0 跳过；否则取 `dispatchOrder(...).eligible` 的前「空位」个。各池结果依次拼接。`poolId` 不对应任何 limit 的排队条目忽略（由调度引擎按「池已被删除」处理）。

**需求里的例子必须写成测试：** 容量 20，甲项目在跑 12、排队 10，乙项目在跑 0、排队 10，此刻空位 8 → 放行的 8 个全部来自乙。

### 3.4 `queuePositions(limits, running, queued): Map<string, number>`

每个池：`eligible` 依次编号 1、2、3……，接着 `blocked` 继续编号。返回 运行编号 → 位置。池不存在的排队条目不出现在结果里。

### 3.5 `findExpired(runs, now: number): Expiry[]`

`now` 是毫秒时间戳（调用方传 `Date.now()`），和运行里的 ISO 时间用 `Date.parse` 比较。

```ts
interface TimedRun {
  runId: string;
  status: "queued" | "running";
  queuedAt: string;
  startedAt: string | null;
  timeoutMs: number;
  queueTimeoutMs: number | null;
}
interface Expiry { runId: string; kind: "timeout" | "queue_timeout" }
```

- 工作中：`startedAt` 非 null 且 `now − startedAt ≥ timeoutMs` → `timeout`。
- 排队中：`queueTimeoutMs` 非 null 且 `now − queuedAt ≥ queueTimeoutMs` → `queue_timeout`。
- 时间解析不出来的条目跳过，不抛异常。输出顺序同输入。

### 3.6 `canTransition(from, to)` / `assertTransition(from, to)`

允许的只有六条：排队中 → 工作中 / 已取消 / 失败；工作中 → 已完成 / 失败 / 已取消。其余一律不允许（包括原地不动）。`assertTransition` 不允许时抛 `FleetError("illegal_transition", "不能从「<中文状态>」变为「<中文状态>」")`，中文取 `STATUS_LABELS`。

### 3.7 `resolveRunOutcome(input): ResolvedOutcome`

```ts
type ProcessExit =
  | { kind: "exited"; code: number | null; signal: string | null }
  | { kind: "lost" }; // 服务重启后发现进程已不在，拿不到退出码
interface OutcomeInput {
  progress: RunProgress;   // 见 runtimes/types.ts
  exit: ProcessExit;
  killedBy: KilledBy;      // "cancel" | "timeout" | null
  timeoutMs: number;
}
interface ResolvedOutcome { status: TerminalStatus; failReason: FailReason | null; message: string | null }
```

按顺序判断，命中即返回：

1. 事件流已给出已完成（`progress.outcome?.status === "completed"`）→ 已完成，原因和说明都是 null。活已经干完，哪怕随后被取消或超时也如实算完成。
2. `killedBy === "cancel"` → 已取消，说明「已被取消」。
3. `killedBy === "timeout"` → 失败 `timeout`，说明「运行超过 <N> 分钟被结束」，N = `timeoutMs / 60000` 取整（不足 1 按 1）。
4. 事件流给出失败 → 失败，原因和说明取自 `progress.outcome`。
5. `exit.kind === "lost"` → 失败 `interrupted`，说明「服务重启后找不到苦工进程，输出里也没有正常收尾」。
6. 退出码非 0 且非 null → 失败 `exit_code`，说明「进程退出码 <code>」，有 `plainOutputTail` 时追加「：<tail>」。
7. 退出码为 null 且有 `signal` → 失败 `exit_code`，说明「进程被信号 <signal> 结束」。
8. 退出码 0 但事件流没给结局：
   - 有 `plainOutputTail` → 失败 `runtime_error`，说明 = `plainOutputTail`（例：运行时只打印一行错误提示就以 0 退出；pi 缺密钥时实际是退出码 1，走第 6 条）；
   - 否则有 `finalText` → 已完成；
   - 否则 → 失败 `runtime_error`，说明「进程正常退出，但没有任何模型输出」。

## 4. 验证方式

`packages/core/test/scheduling/`、`packages/core/test/lifecycle/` 下单测，至少覆盖：

- dispatchOrder：单项目先来先到；两项目交替；占用少的优先；并列时队首早的优先；单项目上限挡住后进 blocked；其他池的条目被忽略；空输入。
- planDispatch：容量上限；需求里 12/8 的例子；容量 0（暂停）；容量调小导致在跑数超过容量时不放行；多个池互不影响；池不存在的条目被忽略。
- queuePositions：与 dispatchOrder 一致；blocked 排在后面。
- findExpired：恰好到点算超时；排队不限时从不超时；非法时间跳过。
- transitions：6 条允许 + 全部不允许组合（5×5 穷举）；报错信息是中文状态名。
- resolveRunOutcome：8 条规则各至少一个用例，外加「完成后又被取消」「超时但事件流已完成」。
