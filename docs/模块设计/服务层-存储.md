# 服务层 · 存储

> 模块定位：把项目、苦工、运行三类记录存进本机 SQLite，给调度引擎提供读写接口 · 对应代码：`packages/daemon/src/store/` · 所属里程碑：[M1 闸门服务与 fleet 命令](../roadmap.md#m1)、[M5 第二版底座](../roadmap.md#m5)（过期清理的查询在 [M3](../roadmap.md#m3) 启用）· 状态：已完成（第二版已实现）· 最近更新：2026-09-25

## 1. 职责与边界

- **管：** 打开数据库、建表与迁移、三个仓库（项目、苦工、运行）的读写、事务。
- **不管：** 业务规则（状态能不能变、该不该放行）；原始输出文件（在 `runs/` 目录，由调度引擎管理）。

## 3. 规格

### 3.1 打开数据库

- 用 Node 24 自带的 `node:sqlite`（`DatabaseSync`），同步接口。支持 `":memory:"`（测试用）。
- 文件数据库开启 `journal_mode = WAL`、`synchronous = NORMAL`；都开启 `foreign_keys = ON`、`busy_timeout = 5000`。
- 迁移用 `PRAGMA user_version` 记版本：从当前版本往后依次执行，每个版本一个事务。目前有版本 1、2。
- 父目录不存在时先建。

### 3.2 表结构（版本 1）

```sql
CREATE TABLE projects (
  key TEXT PRIMARY KEY,
  path TEXT NOT NULL,
  name TEXT NOT NULL,
  color_index INTEGER NOT NULL,
  created_at TEXT NOT NULL
);
CREATE TABLE workers (
  id TEXT PRIMARY KEY,
  project_key TEXT NOT NULL REFERENCES projects(key) ON DELETE CASCADE,
  cwd TEXT NOT NULL,
  title TEXT NOT NULL,
  role TEXT NOT NULL,
  runtime TEXT NOT NULL,
  pool_id TEXT NOT NULL,
  model TEXT NOT NULL,
  thinking TEXT,
  session_ref TEXT,
  created_at TEXT NOT NULL,
  latest_run_seq INTEGER NOT NULL
);
CREATE INDEX idx_workers_project ON workers(project_key, created_at);
CREATE INDEX idx_workers_created ON workers(created_at);
CREATE TABLE runs (
  id TEXT PRIMARY KEY,
  worker_id TEXT NOT NULL REFERENCES workers(id) ON DELETE CASCADE,
  seq INTEGER NOT NULL,
  prompt TEXT NOT NULL,
  status TEXT NOT NULL,
  fail_reason TEXT,
  error_message TEXT,
  queued_at TEXT NOT NULL,
  started_at TEXT,
  ended_at TEXT,
  timeout_ms INTEGER NOT NULL,
  queue_timeout_ms INTEGER,
  pid INTEGER,
  process_image TEXT,
  exit_code INTEGER,
  killed_by TEXT,
  usage_json TEXT NOT NULL,
  retry_json TEXT,
  activity TEXT,
  last_activity_at TEXT,
  final_text TEXT,
  event_count INTEGER NOT NULL DEFAULT 0,
  UNIQUE (worker_id, seq)
);
CREATE INDEX idx_runs_status ON runs(status);
CREATE INDEX idx_runs_ended ON runs(ended_at);
CREATE INDEX idx_runs_started ON runs(started_at);
```

### 3.2.1 版本 2（2026-09-24）

```sql
ALTER TABLE runs ADD COLUMN spawned_at TEXT;
```

对应运行记录的 `spawnedAt`：拿到进程号的时刻，用来核对进程号有没有被系统复用（见 [进程托管](服务层-进程托管.md) 3.5）。旧库迁移后已有的运行这一列为 null。

### 3.3 行与记录的转换

- 列名下划线、字段名驼峰，一一对应。`usage_json` ↔ `Usage`，`retry_json` ↔ `RetryInfo | null`。
- **读出时校验**：`status`、`fail_reason`、`runtime`、`thinking`、`killed_by` 必须是契约里的合法值；`usage_json` 的每个字段类型正确。不合法就抛 `FleetError("internal", "数据库记录损坏：<表>.<列> = <值>")`。校验用类型收窄实现，不准用 `as` 强转。
- 写入时 `undefined` 的字段不写；`update` 只更新 patch 里出现的键，patch 为空对象时不执行任何语句。

### 3.4 查询口径

按 `store/types.ts` 注释实现，补充：

- `colorIndicesInUse(since)`：`projects` 联 `workers`，取有 `workers.created_at >= since` 的项目的 `color_index`，去重。
- `deleteOrphansCreatedBefore(before)`：删掉没有任何苦工且 `created_at < before` 的项目。
- `listExpiredWorkerIds(before)`：苦工最新一次运行（`seq = latest_run_seq`）状态是终态且 `ended_at < before`。
- `listByIds` / `listByWorkers` 在编号很多时分批执行（每批 500 个），避开 SQLite 参数个数上限。
- 所有列表查询用预编译语句，参数一律绑定，禁止字符串拼接用户输入。

## 4. 验证方式

`packages/daemon/test/store/` 下用 `":memory:"` 和临时目录里的文件数据库各测一遍：

- 迁移：新库建表后 `user_version = 2`；对已迁移的库再次打开不重复执行；手工造一个只跑过版本 1 的文件库（含一条运行），重新打开后升到 2，原有数据不丢，新列为 null；`spawnedAt` 往返一致。
- 三个仓库每个方法至少一个用例；`update` 只改 patch 里的字段；JSON 列往返一致（含费用 null）。
- 级联删除：删苦工连带删运行；`deleteOrphansCreatedBefore` 不删有苦工的项目。
- 损坏记录：手工写入非法状态值，读出时报中文错误。
- 查询口径：`listActive` 只含排队中和工作中并按排队时间升序；`listExpiredWorkerIds` 只看最新一次运行；`listByIds` 超过 500 个编号仍正确。
- 事务：`transaction` 里抛异常时整体回滚。

## 第二版（M5）：数据库版本 3、统计与任务查询

> 所属里程碑：[M5](../roadmap.md#m5) · 依据：[技术设计 8.3、8.4](../技术设计.md#83-数据库变化版本-3)、[功能清单](../功能清单.md) 8.1～8.10、10.1～10.6 · 记录类型见 `packages/core/src/domain/records.ts`（主控已改）

### A. 升级前备份

`openDatabase`（`db.ts`）在跑迁移之前：如果是文件库、当前 `user_version` ≥ 1 且小于最新版本，先执行 `VACUUM INTO '<home>/db-backups/fleet-v<旧版本>-<时间>.db'`（时间是 ISO 字符串里 `:` 和 `.` 换成 `-`；目录不存在就建；只留最近 10 份，按文件名排序删最旧的）。备份失败就抛错、不迁移。`:memory:` 库和新建库（版本 0）不备份。备份目录路径加到 `app/paths.ts`（`dbBackupsDir`），`openDatabase` 需要能拿到它：给 `openDatabase` 加一个可选参数 `backupDir?: string`，`createRepos` 透传，`startDaemon` 传入。

### B. 迁移机制加一项能力

SQLite 在事务里改不了 `foreign_keys`，而重建表必须先关外键。迁移数组的元素从「SQL 字符串」改成 `{ sql: string; rebuildsTables?: boolean }`（旧的两版照搬，不带标记）。带 `rebuildsTables` 的版本：先在事务外 `PRAGMA foreign_keys = OFF`，再照常 `BEGIN` → 执行 → `PRAGMA foreign_key_check`（有任何一行结果就抛错回滚）→ 写版本号 → `COMMIT`，最后无论成败都 `PRAGMA foreign_keys = ON`。

### C. 版本 3 的 SQL（`rebuildsTables: true`）

1. **workers 重建：** 建 `workers_new`，列为第一版全部列，其中 `pool_id`、`model` 去掉 NOT NULL，另加 `requested_pool TEXT`、`channel TEXT`、`model_name TEXT`（都可空）。搬数据：`requested_pool` 为 NULL；`channel` = `model` 里第一个 `/` 之前的部分，`model_name` = 之后的部分（`model` 里没有 `/` 时 `channel` 取 `pool_id`、`model_name` 取 `model`）。删旧表、改名、重建两个旧索引。
2. **runs 重建：** 建 `runs_new`，去掉 `usage_json`，换成 `input_tokens`、`output_tokens`、`cache_read_tokens`、`cache_write_tokens`、`total_tokens`（都是 `INTEGER NOT NULL DEFAULT 0`）、`cost_usd REAL`（可空）、`run_ms INTEGER`（可空）、`raw_purged INTEGER NOT NULL DEFAULT 0`；其余列和约束照旧（含版本 2 的 `spawned_at`）。搬数据：用量各列用 `json_extract(usage_json, '$.inputTokens')` 等取出（取不到按 0，费用取不到按 NULL）；`run_ms` = `started_at`、`ended_at` 都不为空时 `CAST(ROUND((julianday(ended_at) − julianday(started_at)) × 86400000) AS INTEGER)`，否则 NULL。删旧表、改名、重建三个旧索引。
3. **配色表：** `CREATE TABLE series_colors (kind TEXT NOT NULL, name TEXT NOT NULL, color_index INTEGER NOT NULL, created_at TEXT NOT NULL, PRIMARY KEY (kind, name))`。
4. **新索引：** `workers(pool_id)`、`workers(role)`、`workers(project_key)` 已有复合索引可复用不另建；`runs(worker_id, seq)` 已有唯一约束；另建 `idx_runs_raw_purge(raw_purged, ended_at)`。

### D. 行映射与 repo

- `rowMappers.ts`：苦工的新列 ↔ `requestedPool`、`channel`、`modelName`，`pool_id`、`model` 可空；运行的用量列 ↔ `usage`（读出时逐列校验是有限数字、非负，费用是数字或 NULL，不合法抛 `数据库记录损坏`），`run_ms` ↔ `runMs`。
- `WorkerPatch` 扩成可改 `sessionRef`、`latestRunSeq`、`poolId`、`model`、`channel`、`modelName`（放行时给没点名的苦工定池用）。`RunPatch` 自动带上 `runMs`（它来自 `RunRecord`）。
- **RunRepo 新增：**
  - `listRawPurgeCandidates(endedBefore: string, limit: number): Array<{ id: string }>`：`raw_purged = 0` 且 `ended_at < endedBefore` 的运行，按 `ended_at` 升序。
  - `markRawPurged(ids: readonly string[]): void`。
  - `listStartedBetween(fromIso: string | null, toIso: string): RunRecord[]`（`started_at` 不为空，from 为 null 时不设下限）——快照的 24 小时窗口也可以复用。
- **ProjectRepo：** 不变；`deleteOrphansCreatedBefore` 不再被调用但保留。
- **WorkerRepo：** `listExpiredWorkerIds` 相关的删除路径不再被调用但保留。
- **新 `StatsRepo`（`statsRepo.ts`）**，挂到 `Repos.stats`：
  - `runFacts(sinceIso: string | null): RunFact[]`：`started_at` 不为空且 ≥ since 的运行，只取 `RunFact` 的字段。
  - `workerFacts(sinceIso: string | null, alsoIds: readonly string[]): WorkerFact[]`：`created_at` ≥ since 的苦工，再并上 `alsoIds` 里的（去重，分批 500）。
  - `seriesColor(kind: "model" | "channel" | "role", name: string, nowIso: string): number`：表里有就返回；没有就取同一 kind 已用的位置，用核心层 `pickColorIndex(已用, name)` 选一个插入并返回（插入冲突时重读）。
- **新 `TaskRepo`（`taskRepo.ts`）**，挂到 `Repos.tasks`：
  - `query(input: TaskQueryInput): { workers: WorkerRecord[]; total: number; nextCursor: string | null }`，其中

```ts
interface TaskQueryInput {
  status: TaskStatusFilter;          // 来自 @fleet/core
  projectKey?: string;
  poolId?: string;
  role?: string;
  channel?: string;                  // 按 workers.channel 筛
  modelName?: string;                // 按 workers.model_name 筛
  createdFrom: string | null;        // ISO，含；null 不设下限
  createdTo: string;                 // ISO，不含
  titleContains?: string;
  sort: TaskSortKey;                 // createdAt | runMs | tokens
  order: "asc" | "desc";
  cursor?: string;
  limit: number;
}
```

  - 状态按苦工**最新一次运行**判定（`runs.seq = workers.latest_run_seq`）：`active` = queued 或 running；`retrying` = running 且 `retry_json` 不为空；`all` 不筛；其余等于该状态。
  - `poolId` 按 `workers.pool_id` 筛（没被放行过的公共排队任务 `pool_id` 为空，选了池就筛不到它们）。
  - 标题用 `LIKE '%…%' ESCAPE '\'`，先把 `%`、`_`、`\` 转义。
  - 排序值：createdAt = `workers.created_at`；runMs = 该苦工全部运行 `COALESCE(run_ms, 0)` 之和；tokens = 全部运行 `total_tokens` 之和。排序值相同时按苦工编号，方向和主排序一致。
  - 翻页用游标：`nextCursor` = 本页最后一条的「排序值 + 苦工编号」做 JSON 再转 base64url；下一页条件是 `(排序值, 编号)` 严格在它之后。游标解不开或排序键对不上抛 `FleetError("invalid_request", "翻页参数无效，请从第一页重新加载")`。本页不足 `limit` 条时 `nextCursor` 为 null。
  - `total` = 同样筛选条件下的总数（不受游标影响）。
  - 查询要走索引，不要把全表读进内存再筛。
  - 已知局限（评审确认、有意不改）：按 runMs、tokens 这类合计值排序时，翻页途中某个任务又跑完一次，它的合计值变了，可能在下一页重复出现或被跳过。这是游标翻页的固有限制；任务页每次有任务开始或结束都会从第一页重新拉取，影响很小。

### E. 验证

- `migrations.test.ts`：新库直接到版本 3；用版本 2 的建表语句造一份旧库（含 `usage_json`、带 `/` 和不带 `/` 的 model、有结束和没结束的运行），迁移后各列取值正确、外键完整、`user_version = 3`；迁移中途失败时回滚、版本号不变、外键重新打开。
- `db.test.ts`：文件库从版本 2 升级前生成备份文件，内容是旧库；超过 10 份删最旧；新库、内存库不备份。
- `rowMappers`：新列往返；损坏的用量列报错。
- `statsRepo.test.ts`：两种事实的筛选；`seriesColor` 第一次分配、第二次读回、同一 kind 取最小空位、不同 kind 互不影响。
- `taskRepo.test.ts`：每种状态筛选（含 retrying、active）；项目、池、角色、时间、标题（含 `%` 和 `_`）；三种排序两个方向；翻页走完全程不重复不遗漏，中途插入新苦工也不影响已翻过的页；坏游标；`total`。
- 性能：造 10000 个苦工、30000 次运行，`runFacts(null)` 和 `taskRepo.query` 各跑一次都在 500 毫秒内（测试里断言，留足余量）。
