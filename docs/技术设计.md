# fleet-studio 技术设计

> 最近更新：2026-09-25 · 状态：已定稿（第二版见第八节） · 上游：[需求设计](需求设计.md) · 下游：[架构设计](架构设计.md)、[roadmap](roadmap.md)

## 一、技术选型

| 方面 | 选择 | 为什么 |
|---|---|---|
| 运行时 | Node.js 24（本机 v24.18.0） | 与 pi 同一个运行时；自带 SQLite，免编译原生模块 |
| 语言 | TypeScript 5，最严格档 | 全局规范要求；见第五节的编译选项 |
| 模块格式 | 纯 ESM | 统一一种，少踩坑 |
| 包管理 | pnpm 10 工作区 | 本机已装 10.34.5；多包共用一份依赖 |
| 数据库 | `node:sqlite`（WAL 模式） | Node 24 自带，无原生依赖；单机单进程写入足够 |
| HTTP 服务 | Hono 4 + `@hono/node-server` | 轻、类型完整、自带 SSE 推送工具 |
| 参数校验 | zod 4 | 配置文件和接口入参都要校验；浏览器和 Node 都能跑 |
| 命令行解析 | `node:util` 的 `parseArgs` | 零依赖，够用 |
| 前端 | React 19 + Vite | 生态最熟，子代理写得最稳 |
| 前端状态 | zustand | 一个小仓库装快照，比手写订阅少出错 |
| 前端样式 | CSS 变量（设计令牌）+ CSS Modules | 令牌集中在一个文件；业务样式按组件隔离；门禁可以机械检查写死的色值 |
| 前端交互原件 | Radix UI（Tooltip、Collapsible、ScrollArea） | 自带键盘可达和无障碍属性 |
| 图标 | lucide-react，按白名单使用 | 线性图标，和开发工具气质一致 |
| 格式化与检查 | Biome 2 | 一个工具管格式和静态检查，与 wiki-forge 一致 |
| 单元测试 | Vitest | 与 Vite 同源，TypeScript 直接跑 |
| 截图验收 | Edge + 调试协议截图（ui-build 的工具） | 本机已有 Edge；不引入 Playwright 浏览器下载 |

不选的：Express（类型弱、SSE 要自己拼）；better-sqlite3（要编译原生模块）；Tailwind（令牌落地方式要和门禁检查配合，CSS 变量更直接）；Next.js（纯本地单页，不需要服务端渲染）。

## 二、仓库结构

```text
fleet-studio/
├─ packages/
│  ├─ core/        领域核心：纯函数，零 IO，浏览器和 Node 都能用
│  ├─ daemon/      闸门服务：存储、进程托管、调度循环、HTTP 接口、静态托管看板
│  ├─ cli/         fleet 命令：只通过 HTTP 和服务对话
│  └─ testkit/     假苦工脚本：按剧本吐出 pi / opencode 格式的事件流，给集成测试和演示用
├─ apps/
│  └─ web/         看板前端，构建产物由 daemon 托管
├─ roles/          fleet-studio 自带的角色提示词（目前只有「测试」）
├─ scripts/        门禁、安装命令外壳等工程脚本
└─ docs/           需求、技术、架构、前端设计、roadmap、模块设计、进度、调研
```

**依赖方向（硬规则）：**

- `core` 不依赖任何包内其他代码，不 import 任何 `node:` 模块，不做 IO。
- `daemon`、`cli`、`web` 都只能依赖 `core`，彼此之间不互相 import。
- `cli` 和 `web` 只通过 HTTP 接口和 `daemon` 交流，接口的请求、响应类型统一定义在 `core/src/api/`。
- `testkit` 只被测试和演示脚本使用，生产代码不依赖它。

## 三、数据目录

默认在 `%USERPROFILE%\.fleet-studio\`，环境变量 `FLEET_HOME` 可以改（测试和演示用独立目录，互不干扰）。

```text
.fleet-studio/
├─ config.json        用户配置：池、角色、默认值、端口。第一次启动时按默认值生成
├─ daemon.json        服务运行信息：进程号、端口、本机令牌、启动时间、版本
├─ fleet.db           SQLite：项目、苦工、运行记录（WAL 模式）
├─ daemon.log         服务日志，超过 5MB 轮转一份
└─ runs/
   └─ <运行编号>/           每次运行一个目录
      ├─ task.md          任务太长、需要写文件传给运行时时才有
      ├─ out.jsonl        苦工 stdout 原样落盘（事件流）
      ├─ err.log          苦工 stderr 原样落盘
      └─ timeline.jsonl   解析出的时间线草稿，重新打开看板时直接读它
```

原始输出文件是最终依据；数据库只存汇总字段（状态、用量、最后活动、回报）。时间线草稿边解析边写进 timeline.jsonl，这个文件丢了也能从原始输出重新解析出来，解析规则是纯函数。

## 四、关键技术决策

### 4.1 苦工进程：分离启动 + 输出写文件

苦工以「分离」方式启动，stdout / stderr 直接重定向到 `runs/` 下的文件，服务轮询文件增量来解析。好处：

- 服务重启、崩溃都不会连带杀死苦工；重启后按进程号重新接管，从文件开头重新解析即可还原状态。
- 不经过管道，没有编码转换，中文不会乱码。
- 进程启动时直接调用 `node.exe + pi 的入口脚本`（opencode 同理，调用它的真实可执行文件），**不经过 cmd.exe 和 PowerShell**：多行任务、引号、逗号分隔的工具清单原样送达。
- 服务在拉起苦工前，从注册表补齐用户级和系统级环境变量（只补缺的，不覆盖），解决「后台进程读不到通道密钥」。
- 取消和超时用 `taskkill /PID <进程号> /T /F` 结束整棵进程树。
- 接管时的存活判断：进程号存在且映像名与启动时一致，才认作同一个进程，避免进程号被系统复用后误认。

运行时（pi、opencode）的具体启动参数、事件格式、结果判定和续接方式见 [pi 运行时调研](调研/pi-运行时.md)、[opencode 运行时调研](调研/opencode-运行时.md) 和 [运行时适配模块](模块设计/核心层-运行时适配.md)。

### 4.2 容量调度：纯函数 + 事件触发

「谁占得少谁先补」写成纯函数 `planDispatch`：输入各池上限、在跑列表、排队列表，输出这一刻该放行哪些运行。服务在这些时刻调用它：新派活、有运行结束、配置变化、每秒兜底一次。纯函数意味着所有公平性规则都能用单测穷举。

### 4.3 实时推送：两路 SSE

- 全局一路：连上先推一份完整快照，之后有变化时再推完整快照，最快每 300 毫秒一次。快照在 100 个苦工时约几十 KB，本机传输无压力，前端也不用做增量合并，最不容易错。
- 单个苦工一路：打开详情时连上，从指定位置开始推时间线事件增量。

### 4.4 安全

- 只监听 `127.0.0.1`。
- 所有请求校验 `Host` 必须是 `127.0.0.1:<端口>` 或 `localhost:<端口>`，防 DNS 重绑定。
- 带 `Origin` 头的请求，来源必须是看板自身，防网页跨站调用。
- 会改变状态的接口（派活、续接、取消、改容量）必须带 `X-Fleet-Token`，令牌在服务首次启动时随机生成，写在 `daemon.json`，命令行自动读取。第一版看板只读，不持有令牌；第二版看板持有一个只能启停池和调顺序的看板令牌，见 8.6。

### 4.5 编号

- 苦工编号：`w` + 5 位小写字母数字，例如 `w7k2mq`，短到主会话能直接敲。
- 运行编号：`<苦工编号>.<序号>`，例如 `w7k2mq.2`。
- pi 的会话编号固定为 `fleet-<苦工编号>`，续接时复用；opencode 的会话编号从首次运行的事件流里取。

### 4.6 命令外壳

`fleet` 命令由 `scripts/install-shims.mjs` 写入 npm 全局目录（已在 PATH 中），生成 sh、ps1、cmd 三种外壳，都直接调用 `node <仓库>/packages/cli/dist/main.js`。长任务一律建议用 `--prompt-file` 或标准输入传入，绕开命令行长度和 cmd 换行截断。

## 五、工程规范

### TypeScript

`tsconfig.base.json` 统一开启：`strict`、`noUncheckedIndexedAccess`、`exactOptionalPropertyTypes`、`noImplicitOverride`、`noImplicitReturns`、`noFallthroughCasesInSwitch`、`noPropertyAccessFromIndexSignature`、`useUnknownInCatchVariables`、`verbatimModuleSyntax`、`isolatedModules`。Node 包用 `module: NodeNext`；前端用 `moduleResolution: Bundler`。

### 代码组织

- 一个文件只干一件事，超过 300 行就该拆。
- 只用具名导出；React 组件文件也用具名导出。
- 目录按职责划分（见各模块设计），不按「types / utils」这种技术类别堆放。
- 错误统一用 `FleetError`（带 `code` 和中文 `message`），接口层把它转成 `{ error: { code, message } }`。
- 时间在数据库和接口里一律存 ISO 8601 UTC 字符串；显示时转本地时间。
- 注释写「为什么」，不复述代码。

### 前端

- 所有颜色、字号、间距、圆角、阴影、时长只能来自 `apps/web/src/styles/tokens.css` 的 CSS 变量。门禁会检查业务样式里有没有写死的色值。
- 每个组件处理长文本溢出、空状态、加载状态、错误状态。
- 规格见 [前端设计](前端设计.md)。

### 提交

- 约定式前缀 + 中文业务描述，例如 `feat: 容量闸门按占用最少的项目优先放行`。
- 一个提交只做一件事；按模块和里程碑拆分。

| 层 | 测什么 | 怎么测 |
|---|---|---|
| core | 调度、状态流转、结果判定、事件流解析、回报解析、配置校验、快照汇总 | 纯单测；事件流解析用调研时抓到的真实样本当夹具 |

| 下拉框、开关、分段切换、确认框、弹出层 | Radix UI 的 Select、Switch、ToggleGroup、AlertDialog、Popover | 和第一版同一套原件，自带键盘操作和无障碍属性 | — |

### 8.2 配置文件变化

- 池在数组里的先后就是派活优先级；每个池加一项「启用」，默认启用。
- 配置里的「默认池」不再使用：旧配置里写了照样能读，读到就忽略，也不再检查它指向的池是否存在。
- 保留期改名为「原始输出保留天数」，默认 7；读到旧名字时按新名字处理。任务记录和时间线不再按天删除。
- 看板改设置时，服务先把当前配置复制到数据目录下的 `config-backups/`（文件名带时间，只留最近 50 份），再写临时文件、改名替换（写到一半断电也不会留下半个文件），最后走已有的配置热更新。只改池的顺序和启用两项，其余字段和写法原样保留。

### 8.3 数据库变化（版本 3）

- **苦工表**加两列：渠道（派出时从池配置记下；旧记录按当前配置补齐，池已经删掉的用池编号代替）、点名的池（没点名为空）。池、模型、渠道三列在排队期间可以为空，派出时写入，续接沿用。SQLite 改不了已有列的「不许为空」，这次迁移按「建新表、搬数据、换表名」做。
- **运行表**把用量从一段 JSON 文本拆成数字列（输入、输出、缓存读、缓存写、合计），再加一列「真正在跑的毫秒数」（结束时写入）。统计直接在库里求和，不再逐行解析文本。旧记录迁移时一并补齐。
- **配色表**新建：模型、渠道、角色各自第一次出现时分配一个颜色位置并记下来（规则见 [前端设计 3.8](前端设计.md#38-图表第二版)），保证全站同一个名字同一种颜色。
- 新增索引：按创建时间、开始时间、项目、池、角色、状态查任务。

### 8.4 统计与任务查询

- **统计接口**一次返回总览需要的全部统计：四个统计数和各自的今日数、token 分布（按所选维度，前 8 名加「其他」）、按项目的任务次数分布、token 趋势（按时间分段）。
- **口径：**
  - 任务就是一个苦工会话，续接不另算，按创建时间归到哪一天。
  - token 和耗时按每次运行的开始时间归段。
  - 耗时是运行开始到结束的时间，还在跑的算到当前。
  - 平均耗时 = 总耗时 ÷ 至少跑过一次的任务数，还在排队、一次都没跑过的任务不参与平均。
- **分段：** 今日按小时，近 7 天和近 30 天按天；「全部」和自选日期看跨度，2 天以内按小时，90 天以内按天，更长按周。一律按服务所在机器的本地时间切分，和第一版「今日用量」的算法一致。分段、补齐空段、前 8 名合并「其他」都写成核心层的纯函数。
- **任务查询接口**支持按状态、项目、池、角色、时间筛选，按标题搜索，按开始时间、耗时、用量排序，每页 50 条。翻页用游标：记住上一页最后一条的排序值和编号，中途有新任务插进来，也不会重复或漏掉。
- **实时：** 全局快照流照旧推实时的部分：槽位占用、在跑和排队的任务、公共排队数。统计和任务列表走普通请求；页面从快照里看到有任务开始或结束，就重新拉一次，统计最快 5 秒一次，任务列表第一页最快 2 秒一次。
- **性能目标：** 一万个任务、三万次运行时，统计和任务查询都在一秒内返回，集成测试造数据验证。

### 8.5 按优先级派活

- 放行规则的输入改成：按优先级排好的池（带启用状态）、在跑的运行、排队的运行（每条带着点名的池，没点名的为空）。
- 按优先级逐个池处理。一个池启用且有空位时，候选就是「点名它的排队」加上「没点名的排队」，照旧按「谁占得少谁先补」挑人；挑中没点名的，就把这个池分配给它。
- 新派一个没点名的活，马上跑一次放行：哪个池有空位就被它接走，所有池都满了就留在公共排队。
- 点名了停用的池，或者续接时原来的池已经停用：派活接口直接报错，新增错误类型「池已停用」。
- 停用只挡住新的放行，不打断在跑的苦工，和容量调小走同一套逻辑。
- 排队位置：点名的，按这个池的排队算；没点名的，按公共排队的先后算。

### 8.6 看板的写权限

- 服务把看板首页发给浏览器时，往页面里写一个「看板令牌」。它在每次服务启动时随机生成，和命令行用的本机令牌是两个。别的网站读不到这个页面的内容（浏览器的同源规则），再加上已有的来源和主机名检查，只有本机看板拿得到它。
- 看板令牌只能调两个接口：启停某个池、调整池的顺序。派活、续接、取消、改容量仍然只认命令行的本机令牌。

### 8.7 命令行

- 派活命令不点名池时按优先级挑；输出里写派到了哪个池，或者「排队中，等任一池空位」。
- 查看池的命令按优先级顺序列出，加「优先级」和「状态（启用 / 停用）」两列，结构化输出同步加这两项。
- 打开看板的命令默认打开总览页。

### 8.8 测试

| 层 | 新增要测的 |
|---|---|
| core | 按优先级挑池、满了顺延、公共排队里的公平、点名停用的池、停用后不再放行、续接沿用原池；统计分段、补齐空段、前 8 名合并「其他」；配色分配 |
