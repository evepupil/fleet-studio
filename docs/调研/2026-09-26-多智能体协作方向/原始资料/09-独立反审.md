# 09｜独立反审：多智能体协作方向

**核对日期：2026-09-26。**本文只作方向反审，不代写需求或替产品拍板。

## 证据边界

【Fleet 本地源码观察】`packages/core/src/domain/records.ts` 将 Worker 与单次 Run 分开记录；`status.ts` 中运行状态为 queued、running、completed、failed、cancelled；`submit.ts` 新建记录后请求调度。界面已有任务监控与少量资源设置。`cwd` 是指定工作目录；`spawnWorker.ts` 将它传给子进程，不能据此认定有沙箱或文件权限隔离。自动 worktree 管理未确认。未检索到业务验收、父子依赖状态的证据，但这不是“功能不存在”的证明。

【官方原文】Multica 把工作项与执行区分：“An issue is the persistent record of a piece of work; a run is one concrete run by an agent.” 同一 issue 可有多次 run，完成一次 run 不等于 issue 完成（https://multica.ai/docs/issues，查看日期：2026-09-26）。Squad 是一名 leader 加成员；分配 issue 不会让所有 agent 同时启动，leader 停止后也不亲自实现（https://multica.ai/docs/squads，查看日期：2026-09-26）。其安全文档写明默认子进程继承 daemon 操作系统用户的完整权限，且“不保证文件系统沙箱”（https://multica.ai/docs/security-model，查看日期：2026-09-26）。这说明 `cwd`、工作区与安全边界必须分开讨论。

【官方声明，未实测】Paperclip README 称任务领取与预算执行是原子的、支持定时 heartbeat 和事件触发，并明确“Paperclip orchestrates work, not pull requests. Bring your own review process.”（https://github.com/paperclipai/paperclip，查看日期：2026-09-26）。这些是产品声明，不是本次验证出的硬保护。

## 三条路线

1. **继续扩展 Fleet。**若需求仍以监看运行、续接、查日志和调资源为主，保持现状最省成本；只有反复出现跨多次运行的长期工作，才值得补一层业务工作项。建议优先此路线的窄扩展，不先造“公司”或自治军团。
2. **接现成前台。**若使用者需要成熟的 issue、收件箱、审批视图，而 Fleet 继续负责本地执行，可评估用适配层连接；前提是 API、身份权限、数据归属、运行状态映射和许可证均可接受。以上集成条件目前未验证，不能假设能直接插接。
3. **直接采用现成产品。**若其工作流、执行位置、数据处理和权限模型均符合实际环境，且愿意接受整套控制面，再比较 Multica/Paperclip。Multica 源码许可证写明不得用其代码向第三方提供托管服务，单一组织内部使用不需商业许可（https://github.com/multica-ai/multica/blob/12f8f3f31111564e5e1b9aac3f7f916e8bba4039/LICENSE，查看日期：2026-09-26）；这不等于已核实其托管产品条款或 Fleet 集成兼容性。

## 最小能力与风险验收

要管理多路长期工作，建议先只补五项：①独立于进程的持久工作项，记录目标、上下文、负责人和优先级；②单独的业务状态（待办、进行中、阻塞、待验收、完成），完成不是进程退出；③一个工作项关联多次运行，可查看日志、结果、成本并续接；④明确的阻塞依赖与原子领取，避免重复派活；⑤可附交付证据并由人验收，另设并发、时长和费用上限。现有运行调度与记录可复用；组织层级、自主招募 agent、定时自治、复杂 convoy/DAG、多公司控制面暂不构成最低门槛，先要有真实重复场景再评估。

三类高风险失败及可验收控制：

- **把运行结束误当任务完成。**成功但无交付物的运行不得自动标为业务完成；交付先进入待验收，保留验收人和证据。
- **重复执行或依赖提前放行。**并发领取同一工作项时只能一个成功；下游在上游交付被接受/集成前保持阻塞，不能仅凭 agent 报告结束解锁。
- **费用失控或越权访问。**设置并发、重试、时长/费用硬上限；到限后停止新派发并留审计记录。用受限账号/容器和哨兵文件、凭据验证访问边界；不能把工作目录当沙箱，也不能把 README 预算承诺当验证结果。

## 反转条件与阻塞

若真实工作始终是短小、互不依赖、无需验收的运行，应推翻“加工作项层”的建议，保留监控台。若多团队持续需要自治调度、周期任务、明确治理审批，且产品实测证明权限、预算和数据边界满足要求，才应转向接前台或直接采用。若实测集成成本高于小型原生工作项层，也应放弃接前台。

本轮只做已有源码与公开文档证据反审，未实测集成、预算硬停、沙箱效果或产品版本行为。检索/抓取过程中有外网查询失败，Gas Town 相关证据未补齐；不据此判断其功能有无。
