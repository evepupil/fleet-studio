# 派活效果对比：sonnet 原生子代理 vs dsf 苦工

> 对比对象：本项目（fleet-studio，2026-09-23 至 09-24，全部派给主会话的 sonnet 原生子代理）和 wiki-forge（2026-09-22，派给 pi / opencode 上的 dsf，即 deepseek-v4.1-flash）
> 依据：两个项目各自的 `docs/进度/` 流水、提交记录、主会话验收记录 · 最近更新：2026-09-24（截至 M1 完成）

## 先说局限

- 两边各只有一个项目，项目也不一样：wiki-forge 的 M0 是配置校验和建表生成，基本是纯函数；本项目有进程托管、并发调度、本机服务、实时推送和看板，难度高一档。问题个数不能直接比，只能比问题的**类型**和**被谁发现**。
- 两边的主会话做法也不同：本项目主会话先把各路共用的接口契约、看板令牌和演示数据亲手写成代码，每路的规格写到逐条可验收，这本身就会抬高一次通过率。
- 前端这一项，本项目的看板用户还没看过、没打分，下面只写验收脚本和截图能证明的部分。

## 逐项对比

| 看什么 | dsf（wiki-forge） | sonnet（本项目） |
|---|---|---|
| 一次能接多大的活 | 一轮一小块：M0 共 6 轮派活，合计 134 个测试 | 一路一整块：调度引擎一路约 20 个文件、110 个测试；fleet 命令一路 160 个测试；集成测试一路写了 1500 多行（起真服务的测试台加 22 个测试） |
| 交回时的自检 | 6 轮自检全绿、全部一次验收通过，其中 1 轮主会话顺手改了个测试夹具名 | 写代码的各路交回时自检全绿；主会话验收时退回 2 路（假苦工成功剧本的回报格式、左栏直达链接时所在组不展开），各返工 1 次通过 |
| 漏到后面才被发现的问题 | 交叉评审抓到 4 个校验漏洞（唯一键两字段可相同、参数名与固定列撞名、放行 NaN、特殊名字绕过文案检查），都是边界输入类 | 独立评审抓到调度引擎 3 个并发问题、服务启动半途失败不清理；端到端验收抓到 fleet 命令 2 个严重问题（长时间等待必然失败、退出时崩溃）和 7 个一般问题，另有真实模型的两种写法看板不认；集成测试抓到会话编号丢失；看图验收抓到 3 个界面问题。**这些大多是「两件事撞在同一时刻」「苦工跑得久」或「真实模型的写法」才会出现的**，各路自己的测试一个没抓到 |
| 自己抓到的问题 | —— | 调度引擎路做身份核对时，自己在集成测试里抓到接管收尾会漏读最后一段回报；测试路在全仓负载下自己查出并修掉三处测试时序问题；上一轮说错的一句（会话编号仍会丢）按要求拿证据复测后明确撤回 |
| 对规格的质疑 | 纠正过任务书里一个举例错误 | 质疑多、质量高：opencode 路指出附件参数在调研报告里查无出处，主会话顺着查出参数顺序写错；界面地基报 7 条规格疑点，3 条成立；容量条报 4 条疑点，都处理得合理；左栏自己报出直达链接不展开 |
| 主会话的规格问题 | —— | 写错 2 处：把 pi 的「本轮结束」事件当成只出现一次（真实抓包里一次运行出现 11 次）；opencode 附件参数顺序。前者两个运行时适配共 125 个测试全绿也没暴露，是评审路拿真实抓包逐行回放发现的。漏想 3 处：回报解析没考虑真实模型把段名单独写一行；进程只凭进程号加映像名认人，没考虑 Windows 很快复用进程号（服务重启接管时可能误杀无关进程，主会话用验收场景坐实）；身份核对的规格没先量成本（一次 1.7 秒），取消变慢、接管期间持续吃 CPU，验收时量出来返工 |
| 前端 | 站点功能完整，视觉用户打 1 分；视觉子代理自动打分被证实不可信，前端改由人工接手 | 按逐像素的实现规格派 5 路（地基 + 4 块），交互检查 19 项全过、四个场景 × 四档宽度 × 深浅主题 18 张截图无溢出，看图后 3 处小修。**用户还没打分** |
| 中断与续接 | 前一场会话因模型配置问题两度崩溃，从头再来 | 网关 502 三次、sonnet 用量上限两次、会话重启一次，每次都带着上下文续接，不用重新交代；但用量上限那次流水线空转约一个半小时 |
| 时长与花费 | 花费低 | 从拿到授权到交付约 13 小时（含约 2 小时中断）；各路回报的用量累计超过 900 万 token，单价远高于 dsf |
| 主会话介入业务代码 | 1 次 | 0 次 |

## 结论

1. **sonnet 的明显优势是单次能接的活大、看得懂长规格**：一路就能吃下一个带并发和进程的子系统，还能反过来指出规格的错。主会话拆活的粒度可以粗很多，调度轮次少很多。
2. **两边共同的短板一样**：自己写的测试只覆盖「立即返回、互不干扰」的情形。并发撞车、长时间等待、真实模型的写法习惯，这三类问题两边都靠独立评审、集成测试和接真实环境的验收才抓到。换成贵的模型，这几道关一道也不能省。
3. **规格的错比苦工的错更贵**：本项目最严重的几个问题都出在主会话写的规格上（事件只出现一次的假设、进程号不会复用的假设、没量成本的核对方案），测试全绿照样藏着。对策是评审路拿真实抓包回放、主会话用验收场景坐实风险、动手前先量关键操作的成本，光多写测试解决不了。
4. **前端差异目前说明不了模型档次**：本项目换了做法（先调研、出方向图、主会话亲手写令牌和演示数据、规格写到像素级），效果要等用户看过打分才算数。

## 建议的用法

- **用 sonnet 或更强的模型**：评审路、集成测试路、带并发或进程的子系统、需要读懂大量既有代码的活。
- **用 dsf**：边界清楚的纯函数、数据整理、成批的同构小活，规格写细，量大价廉。
- **不管用哪档**：独立评审 + 起真服务的集成测试 + 接真实环境的端到端验收三道关都要有；主会话写的规格也要过评审。
- 以后想把更强的模型也纳入统一的容量管理，可以在 fleet 的配置里给它单独开一个池，前提是 pi 或 opencode 能接这个模型。
