# fleet-review

两件事：**评审**（找问题、记下来）和**销账**（照着记录修掉、销掉）。记录都在项目的 `docs/review/`，派活规矩照 `fleet-dispatch`。

评审和销账最好分在两个会话：review 会话只找问题、记账，开发会话照账修。两边靠 `docs/review/` 同步，互不打断。

## 记录文件

| 文件 | 内容 |
|---|---|
| `docs/review/_剩余问题.md` | 常驻总览。第一行是 review 进度抬头：上次 review 结尾的 commit id。下面只记两样：还没解决的问题；用户拍板决定不改的问题（带原因）。已解决的直接删掉 |
| `docs/review/YYYY-MM-DD-<简述>.md` | 单次记录。开头写本次的起止 commit id，下面列本次发现的全部问题 |

每条问题写：编号、`文件:行号`、问题、什么输入或情况下会出错、严重程度（严重 / 一般 / 轻微）、状态（未解决 / 已解决 / 不改：原因）。编号在单次记录里连续，总览里带上来源，例如 `0924-3`。

## 评审

1. `docs/review/` 不存在就建。
2. **定区间**：起点取总览抬头记的 commit；第一次 review 还没有抬头，问用户从哪开始。终点取当前最新 commit。用户另给了范围就按用户的。
3. **分路**：`git diff --stat <起点>..<终点>` 看改了哪些地方，按模块或分层切成几路，每路的改动量控制在一个评审看得透的范围。切法写进单次记录。
4. **派评审**：每路一个 `reviewer` 苦工（只读、不联网）。任务书写清项目路径、区间、这一路负责的文件、相关的设计文档，以及重点看什么：正确性、边界输入、几件事同时发生、错误处理、有没有偏离设计。重要模块再加一路换家模型评（fleet-dispatch 第二节）。评审全是只读，可以全部并行。
5. **判真伪**：回来的问题逐条核，能说出「什么输入导致什么错误结果」的才算。拿不准的派一路侦察或测试去复现，别凭感觉收。误报划掉，在单次记录里注明理由。
6. **写两处**：单次记录完整列出本次成立的问题；总览里增量追加。然后把总览抬头改成本次的终点 commit。
7. **汇报**：本次区间、成立几条（按严重程度分）、误报几条、最要紧的三条。

review 会话只记账，不动业务代码。

## 销账

照着 `_剩余问题.md` 一条条处理：

1. 挑出要修的，按文件归组，编号后派给 `fixer` 苦工：每条写清文件、位置、什么输入会出错、期望结果。同一批文件只派一路，不同文件的可以并行。
2. 验收修复：读改动、亲自跑验证；涉及正确性的派 `reviewer` 复评，最好再派 `tester` 补一条能复现原问题的测试。
3. 修复者拒绝的条目看它的理由。你也说服不了自己的，多半是误报：总览里改成「不改：误报，理由……」，单次记录同步。
4. **真改掉的**：从总览删掉；单次记录里对应条目标「已解决」，附提交号。
5. **用户决定不改的**：总览和单次记录都写上不改的原因，留作决策记录。
6. 门禁通过后提交，只提交不推送。

总览永远等于「当前剩余问题 + 已拍板的取舍」。

## 分工提醒

- 评审和修复必须是两路：同一路既挑错又改错，等于自己判自己的卷。
- 评审交回的是清单，不是修好的代码；任何评审结果都要你判过才进记录。
- 进度流水照 fleet-dispatch 第九节写。
