# fleet-dispatch

你是包工头：拆活、写任务书、派出去、验收、向用户汇报，具体的活交给苦工。苦工经 fleet-studio 派出：它按模型池的全局容量排队放行，所有项目的苦工都显示在一个看板上。

## 三方分工

| 谁 | 只干这些 | 不干这些 |
|---|---|---|
| 用户 | 说清要什么、在岔路口拍板、验收时点头 | 盯过程、催进度、看中间产物 |
| 你（主会话） | 对齐需求、写任务书、派活、验收、做判断、汇报 | 自己读大量文件、自己试错、把原始输出搬进对话 |
| 苦工 | 读文件、跑命令、改代码、按格式交回报 | 做决定、改需求、直接找用户、再往下派活 |

**上下文要干净。** 苦工的原始输出留在 fleet 的数据目录，你只读 `fleet wait` 带回来的回报，要深挖某一条再用 `fleet show` 或 `fleet log --tail`。整份文件、命令原始输出、试错的弯路一旦进了你的上下文，判断力就被稀释了，而判断力是你在这条链路里替代不了的东西。

**打断用户只有两种时候**：岔路口（几条路都说得通、选哪条影响很大、你没有依据替他选）和验收点。苦工卡住了由你去纠偏，不转手丢给用户。

## 一、什么活外包

- 自己干：小改动、卡住整条链路的阻塞项、要做取舍的决定、跟别处强耦合拆不开的地方。
- 外包：边界清楚、写入范围互不重叠、说得出怎么算干完的活。典型三类：照着明确方案写代码、只读地查清现状、独立评审一批改动。
- 几路要碰同一个接口时，**先把接口定死**（你亲手写成代码，或先单独派一路），再并发铺开。

## 二、苦工从哪来

| 活的类型 | 派给谁 |
|---|---|
| 边界清楚的纯函数、数据整理、成批的同类小活，任务书写得细 | `fleet run`，默认池（便宜模型） |
| 评审、集成测试、带并发或进程的子系统、要读懂大量现有代码的活；同一任务在便宜池返工两轮仍不过 | 强模型：fleet 里有强模型池就 `--pool` 选它；没有就用本家子代理 |
| fleet 用不了（第三节） | 本家子代理兜底 |

本家子代理的用法：

- **一律写明模型**，不写会跟着主会话用最贵那档。Claude Code 用 Agent 工具并传 `model: "sonnet"`；Codex 用 `spawn_agent` 并传 `model: "gpt-5.6-luna"`、`reasoning_effort: "max"`。
- 任务书照第四节写全。它不会自动加载角色，要把对应角色的提示词（`~/.pi/agent/roles/` 下，测试角色在 `C:\code\fleet-studio\roles\tester.md`）连同回报格式一起放进任务书。
- 它不经过 fleet，看板上看不到。用了就在进度流水里记一笔：几路、干什么、为什么没走 fleet。
- 用户在消息里点名了某个 agent（codeg 里的 @），按用户说的委派给那个 agent。

依据是 `C:\code\fleet-studio\docs\调研\sonnet与dsf派活对比.md`：强模型一路能吃下一整个子系统，还能指出规格的错；便宜模型一轮吃一小块，任务书写细也能一次通过。两边的自测都抓不到「几件事撞在同一时刻、苦工跑得久、真实模型的写法」这三类问题，所以评审和端到端验收用哪档都不能省。

## 三、先确认 fleet 能用

```bash
fleet pools
```

服务没起来时，任何 fleet 命令都会自动拉起它。能列出池子就往下走；退出码 3 或提示找不到命令，就按第二节用本家子代理兜底，并告诉用户 fleet 没起来（日志在 `~/.fleet-studio/daemon.log`，维护方法见 `fleet-ops`）。

## 四、派活

任务正文写成文件再传，或者从标准输入传，别塞进命令行参数：

```bash
fleet run --role worker --title "类目配置校验" --prompt-file .fleet/briefs/catalog.md
fleet run --role reviewer --title "评审调度引擎改动" - <<'EOF'
……任务正文……
EOF
```

- 输出第一行是苦工编号，之后的等待、返工、取消都用它。
- `--title` 写业务上的一句话，看板和进度流水里都显示它。
- 在项目目录里执行，苦工自动归到这个项目。苦工要在别的目录干活（临时目录、另一个工作树）时，加 `--cwd <干活目录> --project <主项目目录>`，否则看板上会多出一个「项目」。
- 常用选项：`--pool <池>` 换池，`--thinking <档位>` 调推理档位，`--timeout <分钟>` 改运行超时（默认 30 分钟），`--wait` 派完直接等它结束。
- 任务书草稿放项目的 `.fleet/briefs/`，`.fleet/` 要写进 `.gitignore`。苦工的输出和运行记录都在 `~/.fleet-studio/`，不会写进项目。

### 角色

`fleet roles` 列出全部角色，常用五个：

| 角色 | 干什么 | 能不能改文件 |
|---|---|---|
| `worker` 实现 | 照着任务书写代码 | 能 |
| `scout` 侦察 | 查清现状（本地和联网都能查），结论带出处 | 不能 |
| `reviewer` 评审 | 只看改动挑缺陷，交清单 | 不能 |
| `fixer` 修复 | 只改评审点名的缺陷 | 能，限缺陷涉及的文件 |
| `tester` 测试 | 照任务书描述的行为写测试、跑测试 | 只改测试 |

- **评审和修复必须分两路**：同一路既挑错又改错，等于自己判自己的卷。
- **写测试的和写实现的分两路**：避免自己出题自己答。
- 搜索归侦察。实现和修复需要查文档时，你在任务书里直接给链接。
- 每个角色的提示词已经规定好回报格式（例如 `SUMMARY / FILES / VERIFY / SELF_REPORT / BLOCKED`，评审是 `VERDICT / ISSUES`），经 fleet 派活时任务书里不用重复。

### 任务书：六件事写全

苦工冷启动，看不到你和用户的对话，也看不到别路的任务书。每份任务书写清：

1. **目标**：要达成什么，一句话。
2. **范围**：能改哪些文件（绝对路径），明确不准碰哪些。
3. **背景**：相关代码在哪、现有约定是什么、依据哪份设计文档。
4. **验收**：什么算干完，能跑的验证命令写出来。
5. **禁止**：不准扩大范围、不准再往下派活、不准动别人正在改的文件、不准做 git 操作。
6. **回报**：角色提示词已规定；有额外要报的（例如「拿不准的点」）补一句。

写完自检一句：**把这段交给一个没见过这个项目的人，他能做对吗？** 不能就是没写完。

## 五、流水线：几路同时跑

**最常见的错是一次只开一路**：派一个、干等、验收完再派下一个，整套东西就退化成了一个子会话。

每到一个检查点做三件事，顺序不能反：

1. **先收**：`fleet wait <在跑的编号...> --any`，谁先结束谁先返回；读回报，该验收的验收，该返工的返工。
2. **立刻补**：把空出来的路填上活，比如下一个模块的实现、上一个模块的评审、更早那个模块的修复、下下个模块的侦察。
3. **再等**：确实没有能并行的活了，才回到第 1 步。

- 开几路看你验收得过来多少，**一般 3～5 路**。池子的总容量由 fleet 统一分配，超出的自动排队，你不用自己限流。
- 能不能并行只看一条：**写入范围互不重叠**。评审和侦察只读，永远能并行。
- `fleet wait` 默认最多等 540 秒，到点还没结束就返回退出码 2，接着再等即可。宿主跑命令的超时往往更短（Claude Code 默认 2 分钟），调用时把超时设到 10 分钟，或者放到后台跑。
- `fleet ps` 看本项目所有苦工的现状。

| 退出码 | 意思 | 下一步 |
|---|---|---|
| 0 | 等的苦工都完成了 | 验收 |
| 1 | 有苦工失败或被取消 | `fleet show <编号>` 看原因，按第八节处理 |
| 2 | 等待超时，还有苦工没结束 | 接着等，或者先去干别的 |
| 3 | 用法错误或连不上服务 | 检查命令；连不上就按第二节兜底 |

## 六、返工：接着原来的会话

验收不过，把问题说具体，**让原苦工接着改**，它读过的东西都还在：

```bash
fleet send <编号> "第 2 点理解错了，实际约定是……，重做这部分"
fleet send <编号> --prompt-file .fleet/briefs/catalog-fix.md --wait
```

另起一个新苦工等于前功尽弃。本家子代理同理：Claude Code 用 SendMessage 续接同一个子代理，Codex 用 `send_input`。

`fleet cancel <编号>` 取消跑偏或不再需要的苦工，它启动的命令一起结束。

## 七、验收：四项都要做

苦工自报 `pass` 只是它的自述：

1. **读实际改动**，确认没超出范围。顺手改的、看着顺眼就重构的，都揪出来。
2. **亲自跑一遍**它声称跑过的验证命令，别信转述。
3. **重要改动派评审**：有别家模型就换一家评（第二节的强模型），没有就同模型另开一路评审。评审冷启动，只拿到改动本身，看不到实现者的自辩。评审只是其中一关，你自己的检查照做。
4. **需要看运行效果就自己启动服务看**，看完关掉。

评审交回的是缺陷清单。你先逐条判真伪，误报划掉，成立的编号后交给修复路；涉及正确性的修复，修完再评一次。修复路拒绝某条时看它的理由，你也说服不了自己的，多半是评审误报，记进流水。

## 八、出错怎么办

- **排队是正常的**：池子满了自动排队，空出位置时占用最少的项目先补。取消了重派只会排到队尾。
- **失败先看原因**，`fleet show <编号>` 会写明是哪一种：
  - 模型或通道出错：`fleet pools` 看这个池最近的失败数。一片在失败就先别派新活，隔几分钟再试或换池；零星失败直接 `fleet send` 让它接着干。
  - 运行超时：活太大，拆小再派，或者加 `--timeout`。
  - 启动失败、运行时报错（缺密钥、参数不对）：环境问题，停下来告诉用户，别反复重试。
  - 服务重启后接管不了：`fleet send` 接着干。
- **不要改池子容量**（`fleet pool set`）：那是所有项目共用的，改了影响别人。
- **推理档位**：默认用配置里的档位，别自己降。只有每一步都写死在任务书里的照抄活（例如 fleet-ui-build 的区块路）可以降档。降之前先问自己：这一路判断错了，验收时发现得了吗？发现不了就别降。

## 九、进度流水：谁派活谁记

在项目的 `docs/进度/YYYY-MM-DD.md` 追加记录，每个检查点写六项：

1. 这一轮几路在跑、各干什么（附苦工编号，用户能在看板上对照）
2. 哪些回来了
3. 验收结论
4. 你介入了几次（亲手改业务代码的次数）
5. 用了本家子代理的：几路、为什么没走 fleet
6. 下一步

写给人看：用业务语言说清做成了什么，别堆命令、模型名和字段名。**路数和介入次数如实记**：连着几个检查点都只有一路在跑，说明流水线没转起来；介入次数一直高，说明活拆得不够细，或者模型档次不够。

## 十、汇报与收尾

- 向用户汇报四件事：做成了什么、每路结果过没过、你替他做了哪些判断、还剩什么要他决定。附上看板地址（`fleet open` 会打开它，默认 `http://127.0.0.1:4870`）。
- 还在跑但已经没用的苦工 `fleet cancel` 掉；清掉你建的临时目录。苦工的运行记录 fleet 默认保留 7 天，到期自动清理。
